# Публикация и откат

## Файлы подписки

| файл | формат | клиент |
|---|---|---|
| `nodes.txt` | plain, одна ссылка в строке | любой, удобно копировать |
| `v2ray.txt` | base64 от `nodes.txt` | v2rayNG, Hiddify, NekoBox |
| `clash.yaml` | mihomo/clash, группы `AUTO` (url-test) и `FALLBACK` | Clash, mihomo, Stash |
| `index.json` | метаданные: время, количество, уникальные подключения | мониторинг |
| `hy2.txt` | только hysteria2 | отдельный профиль |

В `clash.yaml` две группы: `AUTO` (`url-test`, 120 с, допуск 80 мс) и `FALLBACK`
(`fallback`), правила ведут в `FALLBACK` — мёртвая между проверками нода не даёт
таймаут.

## Как публикуется

`publish_pub.py` отправляет файлы через GitHub Contents API, затем **читает их
назад** и сравнивает с локальными. Это важно: успешный HTTP-ответ не значит, что
клиент увидит новый файл — бывает кэш CDN, конфликт версий, частичная запись.

```bash
python3 scripts/publish_pub.py         # репозиторий (GITHUB_REPO)
python3 scripts/publish_pub.py --gist  # гист (GIST_ID)
```

Токен: `$PROXY_SUB_HOME/secrets/gist_token` или переменная `GITHUB_TOKEN`.
Нужен scope `gist` и `repo` (contents: write).

Ретраи: `401/403/429/5xx` повторяются трижды. Наблюдалось дважды: GitHub отдаёт
`401` на валидный токен, через минуту тот же токен работает. Без ретрая клиент
остаётся со старым файлом, а ошибка выглядит как «токен сломан».

## Атомарность и откат

```bash
python3 scripts/sub_snapshot.py save    # после успешной публикации
python3 scripts/sub_snapshot.py check   # количество + mihomo -t clash.yaml
python3 scripts/sub_snapshot.py restore # вернуть последний снимок
```

Запись всегда через `.tmp` + `rename`. Снимок хранит 6 последних версий.

`refresh_subs.sh` делает так:

```
publish_sub → rc=0? → snapshot save → check → ok? publish_pub : restore + notify
```

То есть битая подписка не уезжает клиенту, а если уехала — откатывается и
приходит уведомление.

## Защита от деградации

`publish_sub.py` не публикует список, если он короче половины предыдущего.
Исключение — `SUB_ALLOW_SHRINK=1`: вызывающий подтверждает, что старые ноды
проверены и мертвы. Без этого механизм превращается в хранение мёртвого списка.

## Ошибка, которая стоила простоя

Публикация была разбита на два скрипта, и один из них (`publish_pub.py`) не
вызывался в мобильном цикле. Локальный файл обновлялся, клиент тянул старый —
«ни один сервер не работает». Вывод: **цикл считается завершённым только после
чтения назад того, что видит клиент**.
