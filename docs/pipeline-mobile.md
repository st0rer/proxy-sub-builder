# Мобильный профиль (проверка из сети оператора)

Домашний список и мобильный — разные подписки, потому что DPI у оператора
другой. Нода, живая дома, на мобильной сети часто мертва, и наоборот: замер
16.11.2026 — из 40 домашних живых нод 26 недостижимы по TCP с мобильной сети.

## Схема

```
ноутбук/N100 ── ssh ──→ малинка в мобильной сети (ZeroTier)
                          sing-box: N socks-inbound'ов
                          pi_sb_verify.py: TCP → 3 ступени → второй проход
        ←── out.json ─────┘
mobile_push.py: отбор кандидатов, бюджет трафика, публикация
```

## Отбор кандидатов (`mobile_push.pick_candidates`)

Источники складываются в один список с квотами:

| протокол / источник | квота | особенности отбора |
|---|---|---|
| `vless` | 80 | Reality с фрагментацией ClientHello (`10-20,10-20`), отсев битых flow, добор из `all_links.json` с TCP-проверкой на N100 |
| `ss` | 35 | Shadowsocks (включая Shadowsocks-2022), добор из пула с TCP-проверкой на N100 |
| `hy2` | 8 | пенализация UDP 443 без obfs (-5); приоритет нестандартным портам (+3) и obfs (+2) |
| `anytls` | 15 | AnyTLS через sing-box 1.14+ |
| `tuic` | 4 | TUIC v5 |
| «родственники» панели | 40 | тот же uuid/пароль, другой входной адрес (выход 45% vs 8%) |
| хвост `web_links.txt` | 80 | свежие посты телеграм и каталогов с быстрой TCP-проверкой на N100 |

### Расширение пула и быстрая фильтрация на N100:
1. **Предварительный отсев RU-выходов:** ноды с выходом в RU/BY/IR/KP/CN немедленно отсекаются до отправки на малинку, так как для Gemini/Antigravity они гарантированно дают HTTP 400/403 (геоблок).
2. **Быстрый TCP-фильтр на N100 (`filter_live_tcp`):** перед заливкой конфига на малинку N100 опрашивает открытые порты кандидатов (`timeout=1.2с`, 25 воркеров). 100 нод проверяются за 3.5 секунды, отсекая мёртвые адреса. В результате на Raspberry Pi 3 поступают только заведомо живые TCP-узлы, что исключает многоминутный прогон мёртвых нод в фазе `RECOVERY`.
3. **Оптимизация фазы RECOVERY на Pi 3:** повторный проход сокращён с 3 ступеней (15s+18s+10s = 43s) до 2 ступеней (10s+8s = 18s), снижая штраф за недостижимый узел более чем на 55%.

«Родственники» — самая ценная находка: у нод одной панели доля живых с
мобильного оператора **45 %** (5 из 11 адресов) против ~8 % у обычных
кандидатов. Поэтому панели, которые уже отдавали трафик, добираются первыми
(`PI_N_SIB`).

Карантин `mobile_tested.json` — 48 часов, чтобы не тестировать одно и то же,
но и не терять вернувшиеся ноды.

## Защита ресурсов малинки и сборка мусора

Малинка 3B работает в условиях ограниченных ресурсов (Broadcom BCM2837, 4 ядра Cortex-A53, 1 ГБ RAM):
1. **Изоляция в tmpfs (`/run/vpntest`):** никаких лишних записей на SD-карту.
2. **Очистка перед тестом:** `kill_stale()` завершает любые зависшие sing-box, а `sweep()` обрезает логи > 512 КБ и удаляет файлы старше 1 часа.
3. **Оптимизация пула потоков под 4 ядра:** `par = min(4, 4 if avail > 250 else 2)`. Больше 4 воркеров на Cortex-A53 без гипертрединга перегружает планировщик ядра и вызывает троттлинг CPU. Если RAM < 120 МБ, тест отменяется без падения системы.
4. **Объединённый однопроходный конвейер:** проверка гейта Gemini и `exit_ip` объединены в один параллельный проход вместо двух последовательных циклов. При `REQUIRE_EXIT_IP != 1` медленный опрос 3 сторонних API пропускается, что сокращает время фазы с 40+ с до 5–8 с.
5. **Гарантированное завершение:** блок `finally:` вызывает `proc.terminate()` и `proc.kill()`, закрывая все файловые дескрипторы.
6. **Сборщик мусора на сервере:** по завершении цикла на N100 запускается `gc_engine.py`, ротирующий `refresh_yota.log` и очищающий историю тестирования.

## Фильтрация нод для Gemini и Google Antigravity

В мобильном профиле Yota список `nodes-yota.txt` / `yota.txt` фильтруется строгим гейтом без ложных отсевов:
1. **Проверка Antigravity / Cloud Code PA API:**
   `POST https://daily-cloudcode-pa.googleapis.com/v1internal:loadCodeAssist` с пустым JSON-телом `{}` и User-Agent Chrome.
   - HTTP `401 Unauthorized` (или `200`) — локация принята Google, IP чистый и ожидает Bearer-токен.
   - HTTP `400` / `403` — геоблок (Россия/Иран/санкции) либо отказ Cloud Code API (сразу завершает проверку, экономя лишний curl).
2. **Проверка интерфейса Gemini Web:**
   `GET https://gemini.google.com/app`:
   - HTTP `200 OK` (или `302` на `accounts.google.com`) — интерфейс доступен.
   - HTTP `403` или `302` с `Location: ...sorry/index...` — блокировка датацентрового IP или капча анти-бота Google.
3. **Защита от ложного отсева при джиттере 4G:**
   - Если `loadCodeAssist` подтвердил локацию (`401`), а веб-морда Gemini на 4G-радиоканале задержалась с ответом (не отдав `sorry` и `403`), нода **не выбрасывается**, так как для Antigravity и Cloud Code она валидна.
   - Если в текущем прогоне из-за плохой мобильной связи прошло меньше `SUB_MIN_NODES`, `publish_sub.py` подтягивает подтверждённые Gemini-ноды из `mobile_history.json` (возраст < 24 ч). Подписка никогда не голодает.

### Экономия мобильного трафика и приоритет замера скорости:
- Проверка гейта Gemini потребляет всего ~3–4 КБ на ноду (~80 КБ на 25 живых нод, < 1 % бюджета `BUDGET_MB=12`).
- При замере скорости (`live[:SPEED_TOP]`) ноды сортируются с приоритетом `gemini == "ok"`: мобильный трафик (500 КБ/нода) расходуется в первую очередь на ноды, гарантированно работающие с Gemini и Antigravity.
- Переменная `SUB_REQUIRE_GEMINI=1` в `publish_sub.py` отсекает любые ноды без подтверждённого статуса `gemini == "ok"`.

## Бюджет трафика

`BUDGET_MB=12` на прогон:

- проверка задержки и TCP: 101 нода × ~9 КБ ≈ 1 МБ (16 КБ тела только у прошедших);
- проверка гейта Gemini / Antigravity: ~3 КБ на живую ноду ≈ 0.1 МБ;
- скорость: 10 лучших нод (в первую очередь Gemini-валидные) × 500 КБ ≈ 5 МБ;
- остальное — заголовки и повторы.

## Пороговые значения

```bash
SUB_CAPS="vless=60,ss=30,hy2=10,anytls=15,trojan=10,tuic=0,vmess=0"
SUB_MAX_PER_PANEL=6  # до 6 разнородных адресов на панель для мобильного резервирования
SUB_ORDER=tcp        # vless первыми: QUIC у оператора не проходит
SUB_MIN_SPEED=0.03   # МБ/с
SUB_MIN_NODES=3
SUB_ALLOW_SHRINK=1   # разрешить сжатие, если старые ноды проверены и мертвы
SUB_REQUIRE_GEMINI=1 # публикация ТОЛЬКО нод, прошедших гейт Gemini + Antigravity
```

`SUB_ALLOW_SHRINK` нужен потому, что защита от деградации («новый список вдвое
короче — не публикуем») иначе держит заведомо мёртвый список: из 13 нод
прошлого прогона проверку проходили 3.

## Что не проходит и почему

- **hy2 / hysteria2** — QUIC режется оператором: TCP-порт открыт, данные не идут.
  В мобильной подписке hy2 остаётся только как редкое исключение.
- **vmess / trojan** — 0 из 500+ проверенных, отключены потолком `=0`.
- **Цепочка (chain/detour)** поднимает доступность, но не скорость: итог —
  минимум из звеньев. Для hy2 цепочка невозможна вовсе, ей нужен UDP от края
  до края.

## Расписание

`systemd/subs-yota.timer` — 02:30, 10:30, 18:30 UTC. Ноды живут часы: из 13
собранных в 02:33 к 12:17 оставалось 6, из них 4 с трафиком. Три прогона дают
максимальную свежесть 8 часов ценой ~30 МБ мобильного трафика в сутки.

`mobile_watch.sh` (каждые 30 минут) следит между прогонами: читает метрики
монитора на малинке и сравнивает число нод в гисте с локальным файлом.
Тревога — если живых меньше 4 **и** меньше 40 %, либо публикация старше 8 часов.
