# Потребитель подписки: sing-box на роутере (OpenWrt) + pbr

Кроме сборщика в проекте есть вторая половина конвейера — та, что превращает готовую
подписку в рабочий обход блокировок на домашнем роутере. Она живёт отдельно от публикации
и запускается не с роутера, а с машины-обслуживателя (в референсной установке — N100).

```
N100 (cron)                              OpenWrt-роутер
─────────────                            ──────────────
sb_refresh.sh  05:17 UTC
  ├─ скачать подписку (v2ray.txt/nodes.txt)
  ├─ sbgen.py → sing-box конфиг            /etc/sing-box/config.json
  ├─ scp + sing-box check + restart  ───▶  sing-box (tun sb0, gvisor, mtu 1200)
  ├─ фаза 1: полный конфиг → замер          │
  ├─ замер страны выхода и вердикта Gemini  │
  └─ фаза 2: конфиг без мусора ─────────▶  pbr: политика blocked → интерфейс sbtun
                                            hotplug 50-sbtun-route → маршрут + rp_filter
cf-watchdog.sh  */15
  └─ probe cf через clash_api ───────────▶  переключение селектора gcp (cf ↔ auto)
cf_usage.sh     */6
  └─ GraphQL Analytics: расход квоты Worker (мониторинг)
```

## Что чем выбирается

Конфиг создаёт три уровня выбора, а не один:

| тег | тип | назначение |
|---|---|---|
| `auto` | urltest | пул нод подписки, минимум задержки; `interval 1m`, `tolerance 30` |
| `gcp` | selector | путь для Google-доменов: `cf` (своя Cloudflare-нода) ↔ `auto` |
| `proxy` | selector | всё остальное, по умолчанию `auto`; ручное закрепление ноды |

Маршрут в конфиге:

```json
"route": {
  "rules": [
    {"inbound": ["tun-in"], "action": "sniff"},
    {"domain_suffix": ["mtalk.google.com", "connectivitycheck.gstatic.com", "..."], "outbound": "proxy"},
    {"domain_suffix": ["google.com", "googleapis.com", "gstatic.com",
                       "googleusercontent.com", "google.dev", "recaptcha.net"], "outbound": "gcp"}
  ],
  "final": "proxy"
}
```

`action: sniff` обязателен: из tun приходит только IP, без сниффинга доменные правила
не совпадают вообще.

## Две фазы обновления

1. **Фаза 1 — измерительный стенд.** Публикуется полный список (все ноды подписки),
   затем через clash_api каждая нода по очереди выбирается и проверяется:
   - страна выхода (`ip-api.com` через socks этого же sing-box) → ключ `type|server|port`,
     а не тег: теги переназначаются при каждом пересборе;
   - ответ `https://gemini.google.com/app`: `200` = ок, `403` = страна не поддерживается,
     `302` на `google.com/sorry` = анти-бот по датацентровому IP.
2. **Фаза 2 — публикация.** Генератор получает замеры и выбрасывает: дубли (по качеству SNI),
   РФ-выходы, непроверенные ноды (`--strict`) и всё, что сервис не отдаёт (`--require-gemini`).
   Рабочий конфиг подменяется только после `sing-box check`; при провале остаётся прежний.

## Почему своя Cloudflare-нода

Google судит о регионе по собственной базе репутации IP. Выходы мелких VPS (free-ноды) он
либо относит к РФ, либо помечает как анонимайзер — и отдаёт «Gemini не поддерживается в вашей
стране» даже авторизованному аккаунту, хотя `ip-api` показывает NL/DE. Выход через Cloudflare
(AS13335) принимается: anycast-адреса геолоцированы корректно и делят репутацию с миллионами
пользователей.

Отсюда правило: своя CF-нода (`secrets/cf_node.json`) добавляется в конфиг отдельным outbound,
никогда не фильтруется подпиской и стоит первой в `gcp`.

## Квоты Cloudflare Workers

Free-план: **100 000 запросов в сутки** (сброс в 00:00 UTC, при превышении — ошибка 1027).

- WebSocket-соединение = 1 запрос (только `Upgrade`); сообщения внутри WS не считаются;
- subrequests — 50 на invocation, одновременных исходящих соединений — 6 на invocation.

Поэтому мультиплексирование всех потоков в один WS не помогает: один invocation держит
максимум 6 исходящих. Расход ≈ числу проксируемых TCP-соединений, и сокращают не «запросы»,
а трафик через воркер: Google-домены отдельным путём, видео (`googlevideo.com`) и фоновые
опросы (`mtalk`, `connectivitycheck`, автофилл, апдейтер, Play) — через пул.

Мерить фактический расход: `cf_usage.sh` (GraphQL `workersInvocationsAdaptive` по
`scriptName` + `date`). Бакет `__unknown__` в той же выборке — неатрибутированные запросы
аккаунта, их тоже нужно смотреть: они жгут общую квоту.

## Эксплуатация

| задача | когда | чем |
|---|---|---|
| обновление нод | 05:17 UTC | `sb_refresh.sh` (cron/таймер) |
| сторож CF-ноды | каждые 15 мин | `cf-watchdog.sh` |
| расход квоты | каждые 6 ч | `cf_usage.sh` |
| ручное закрепление ноды | по необходимости | `PUT /proxies/proxy {"name":"hyst-3"}` на clash_api |

После каждого рестарта sing-box селекторы возвращаются к дефолтам (`gcp → cf`, `proxy → auto`).

## Подводные камни

- **Пароль роутера и id аккаунта CF — только в env/secrets.** `ROUTER_PASS` читается из
  `$VPN_SECRETS/router_pass`, `CF_ACCOUNT_ID`/`CF_WORKER_SCRIPT` — из окружения (см. `env.example`).
- **`urltest` сортирует по задержке** и охотно выбирает «быструю, но отвергнутую» ноду.
  Ноду, которую сервис не отдаёт, надо выкидывать из пула, а не надеяться на ранг.
- **Теги нестабильны между пересборами** — любые замеры привязывать к `type|server|port`.
- **`rp_filter` на tun-интерфейсе** должен быть 0, иначе ответные пакеты отбрасываются.
- **Маршрут в таблице pbr** исчезает при каждом рестарте sing-box — восстанавливается
  hotplug-скриптом роутера (`/etc/hotplug.d/net/50-sbtun-route`), он вне этого репозитория.
- **Вердикт сервиса проверять запросом, а не по стране:** `200` / `403` / `302 → /sorry`
  различаются, и лечатся по-разному.
