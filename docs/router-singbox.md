# Потребитель подписки: sing-box на роутере (OpenWrt) + pbr

Кроме сборщика в проекте есть вторая половина конвейера — та, что превращает готовую
подписку в рабочий обход блокировок на домашнем роутере. Она живёт отдельно от публикации
и запускается не с роутера, а с машины-обслуживателя (в референсной установке — N100).

```
N100 (cron)                              OpenWrt-роутер
─────────────                            ──────────────
sb_refresh.sh  05:17 UTC
  ├─ скачать подписку (v2ray.txt/nodes.txt)
  ├─ sbgen.py → sing-box конфиг            /etc/sing-box/config.json
  ├─ scp + sing-box check + restart  ───▶  sing-box (tun sb0, gvisor, mtu 1200)
  ├─ фаза 1: полный конфиг → замер          │
  │   туннель: -L 11080→socks, -L 11090→clash_api
  ├─ замер: страна выхода + гейт Google     │
  └─ фаза 2: конфиг без мусора ─────────▶  pbr: политика blocked → интерфейс sbtun
                                            hotplug 50-sbtun-route → маршрут + rp_filter
cf-watchdog.sh  */5
  ├─ новые строки геоблока в логе IDE ──▶  (WinRM на мини-ПК, где живёт Antigravity)
  ├─ проба гейта Google с текущего выхода
  └─ ротация селектора gcp ─────────────▶  переключение на ноду с проходящим гейтом
cf_usage.sh     */6
  └─ GraphQL Analytics: расход квоты Worker (мониторинг)
```

Порты обслуживающей машины разведены намеренно: `sb_refresh.sh` занимает `11080` (socks)
и `11090` (clash_api), сторож — `11091` (socks) и `19090` (clash_api). Общий порт означал
гонку: сторож, поднимая свой туннель, сносил туннель замера.

## Что чем выбирается

Конфиг создаёт три уровня выбора, а не один:

| тег | тип | назначение |
|---|---|---|
| `auto` | urltest | пул нод подписки, минимум задержки; `interval 1m`, `tolerance 30` |
| `gcp` | selector | путь для Google-доменов: ноды, прошедшие гейт Gemini (Hysteria2 вперёд, до 8 штук), плюс `auto`; дефолт — первая |
| `proxy` | selector | всё остальное, по умолчанию `auto`; ручное закрепление ноды |

Своя Cloudflare-нода (`cf`) живёт в конфиге отдельным outbound и в `gcp` **не входит**.

Маршрут в конфиге:

```json
"route": {
  "rules": [
    {"inbound": ["tun-in"], "action": "sniff"},
    {"domain_suffix": ["mtalk.google.com", "connectivitycheck.gstatic.com",
                       "update.googleapis.com", "playstoregatewayadapter-pa.googleapis.com",
                       "..."], "outbound": "proxy"},
    {"domain_suffix": ["google.com", "googleapis.com", "gstatic.com",
                       "googleusercontent.com", "google.dev", "antigravity.google",
                       "recaptcha.net"], "outbound": "gcp"}
  ],
  "final": "proxy"
}
```

`action: sniff` обязателен: из tun приходит только IP, без сниффинга доменные правила
не совпадают вообще.

## Две фазы обновления

1. **Фаза 1 — измерительный стенд.** Публикуется полный список (все ноды подписки),
   затем через clash_api каждая нода по очереди выбирается и проверяется:
   - страна выхода (`ip-api.com` через socks этого же sing-box) → ключ `type|server|port`,
     а не тег: теги переназначаются при каждом пересборе;
   - гейт Google: `POST /v1internal:loadCodeAssist` → `401` = локация принята,
     `400` = геоблок локации, `403` = бан IP; при неоднозначном ответе — резервный
     `https://gemini.google.com/app` (`200` = ок, `302 → /sorry` = анти-бот).
2. **Фаза 2 — публикация.** Генератор получает замеры и выбрасывает: дубли (по качеству SNI),
   РФ-выходы, непроверенные ноды (`--strict`) и всё, что сервис не отдаёт (`--require-gemini`).
   Рабочий конфиг подменяется только после `sing-box check`; при провале остаётся прежний.

Замер обязан остановиться, если переключение селектора не удалось больше чем для трети
нод: это признак того, что на роутере лежит не тот конфиг, а не того, что ноды мертвы.
Иначе в публикацию уезжает мусорный список.

## Почему своя Cloudflare-нода не спасает

Долгое время считалось, что выход через Cloudflare (AS13335) обходит гео-возражения
Google: anycast-адреса геолоцированы корректно и делят репутацию с миллионами
пользователей. Проверено 18.11.2026 — **для этого гейта не работает**.

Гейт `aicode.googleapis.com` / `daily-cloudcode-pa.googleapis.com` (Antigravity, Code Assist)
режет сам факт прохождения через Cloudflare Workers, независимо от страны выхода:

| что пробовали | результат |
|---|---|
| дефолтный релей воркера (`{colo}.proxyip.cmliussss.net`) | egress плавает HK → DE → SE → RU, вердикт «локация не поддерживается» |
| параметр `?proxyip=<host>` в WS-пути | воркер его игнорирует, egress не меняется |
| привязка `env.PROXYIP` в настройках воркера | egress стабилизируется (SE), вердикт тот же |
| выбор ingress-colo входным CF-IP (`104.16.0.1` → ARN, Стокгольм) | egress SE, вердикт тот же |

Заголовки при этом чистые (`httpbin`: только `Accept`/`Host`/`User-Agent`), `X-Forwarded-For`
и `CF-Connecting-IP` не текут. Значит режется путь через Workers, а не страна релея.

Отсюда правило: Google-домены идут через ноды вне Cloudflare, а `cf` из кандидатов
исключён. Из-за этого же сторож безусловно уводит `gcp` с `cf`, если тот оказался выбран.

## Квоты Cloudflare Workers

Free-план: **100 000 запросов в сутки** (сброс в 00:00 UTC, при превышении — ошибка 1027).

- WebSocket-соединение = 1 запрос (только `Upgrade`); сообщения внутри WS не считаются;
- subrequests — 50 на invocation, одновременных исходящих соединений — 6 на invocation.

Поэтому мультиплексирование всех потоков в один WS не помогает: один invocation держит
максимум 6 исходящих. Расход ≈ числу проксируемых TCP-соединений, и сокращают не «запросы»,
а трафик через воркер: Google-домены отдельным путём, видео (`googlevideo.com`) и фоновые
опросы (`mtalk`, `connectivitycheck`, автофилл, апдейтер, Play) — через пул.

Мерить фактический расход: `cf_usage.sh` (GraphQL `workersInvocationsAdaptive` по
`scriptName` + `date`). Бакет `__unknown__` в той же выборке — неатрибутированные запросы
аккаунта, их тоже нужно смотреть: они жгут общую квоту.

## Эксплуатация

| задача | когда | чем |
|---|---|---|
| обновление нод | 05:17 UTC | `sb_refresh.sh` (cron/таймер) |
| сторож Google-выхода | каждые 5 мин | `cf-watchdog.sh` |
| расход квоты | каждые 6 ч | `cf_usage.sh` |
| ручное закрепление ноды | по необходимости | `PUT /proxies/proxy {"name":"hyst-3"}` на clash_api |

После каждого рестарта sing-box селекторы возвращаются к дефолтам (`gcp` → первая нода
пула, `proxy` → `auto`). Смена селектора не рвёт уже открытые соединения — клиенту нужен
перезапуск, чтобы переподключиться (для Antigravity: `taskkill /F /IM language_server.exe`,
`Stop-Process` иногда молча не срабатывает).

## Подводные камни

- **Пароль роутера и id аккаунта CF — только в env/secrets.** `ROUTER_PASS` читается из
  `$VPN_SECRETS/router_pass`, `CF_ACCOUNT_ID`/`CF_WORKER_SCRIPT` — из окружения (см. `env.example`).
- **`urltest` сортирует по задержке** и охотно выбирает «быструю, но отвергнутую» ноду.
  Ноду, которую сервис не отдаёт, надо выкидывать из пула, а не надеяться на ранг.
- **Задержка ≠ пригодность.** Узел с `220 мс` может отдавать `403` на всё, включая
  `gemini.google.com/app`, — это бан IP целиком (обычно хостинговая подсеть). Сторож
  проверяет именно гейт, а не только задержку.
- **Теги нестабильны между пересборами** — любые замеры привязывать к `type|server|port`,
  а пул сторожа брать из живого селектора, а не хардкодом.
- **`rp_filter` на tun-интерфейсе** должен быть 0, иначе ответные пакеты отбрасываются.
- **Маршрут в таблице pbr** исчезает при каждом рестарте sing-box — восстанавливается
  hotplug-скриптом роутера (`/etc/hotplug.d/net/50-sbtun-route`), он вне этого репозитория.
- **Вердикт сервиса проверять запросом, а не по стране:** `401` / `400` / `403` / `302 → /sorry`
  различаются, и лечатся по-разному.
- **`experimental.unified_delay`** понимает только sing-box ≥ 1.15 (проверено: 1.13.21 и
  1.14.4 отбивают конфиг с `unknown field`). Включать через `SINGBOX_UNIFIED_DELAY=1`.
